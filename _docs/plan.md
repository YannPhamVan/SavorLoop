# SavorLoop — Brainstorming and Initial Project Plan

**GitHub repository:** https://github.com/YannPhamVan/SavorLoop  
**Context:** DataTalksClub AI Dev Tools Zoomcamp 2026 final project  
**Planning goal:** Define a useful cooking assistant that can be delivered in approximately 20 hours while demonstrating the engineering skills expected by the Zoomcamp.

> This document captures the decisions and ideas from the initial brainstorming. Open questions are marked as such. This is an initial project plan, not a finalized technical specification.

## 1. Project overview

**SavorLoop** is a cooking assistant that helps users cook with ingredients they already have, prioritize ingredients that may otherwise go to waste, and build on recipes they have actually prepared.

The name refers to the cooking feedback loop: suggest a recipe, cook it, provide feedback, and use that feedback to improve future suggestions.

Proposed README tagline:

> **SavorLoop — An AI-powered cooking assistant that turns your available ingredients and cooking experience into better meals.**

The project should demonstrate a practical application of AI and software engineering with a clear user benefit, rather than being a purely technical demo.

## 2. Agreed functional scope

### 2.1 Ingredient inventory

The application manages two categories of ingredients.

#### Pantry staples

Examples: oil, vinegar, spices, flour.

- Simple status: available / unavailable.
- No precise quantities.
- The application can consider available staples when generating recipes.

#### Rotating ingredients

Examples: courgettes, mushrooms, milk, eggs.

- Precise quantities, including units.
- Expiry or use-by dates are **optional**.
- When date information is available, ingredients with the most urgent dates should be prioritized where appropriate.
- Dates are not required for every item: the goal is to avoid tedious data entry and unreliable guesses.

The inventory must be viewable and editable through a conventional interface. It must also support natural-language updates, for example:

- “I used 200 g of mushrooms.”
- “I’m out of olive oil.”

The AI interprets the request and converts it into a structured operation. Conventional code validates the operation before changing the inventory: the AI must not be allowed to modify stored data arbitrarily.

### 2.2 Recipe suggestions

The application generates recipes on demand, for example in response to “What can I cook tonight?”, and also highlights ingredients that should be used soon.

Suggestions should:

- Prioritize available ingredients and, when the information exists, ingredients that need using soon.
- Balance recipes that can be made from current stock with interesting options requiring one or two additional ingredients.
- Explicitly identify missing ingredients.
- Suggest possible substitutions.
- Provide a complete recipe: ingredients, quantities, steps, preparation time, and serving count.
- Allow the user to adjust the number of servings.
- Briefly explain why the recipe is being suggested, particularly in relation to available stock and urgent ingredients.

Recipes are **generated by AI on demand**. No pre-built recipe catalogue is required at the start.

A generated recipe that has not been cooked is not saved. It disappears after consultation, avoiding a growing backlog of theoretical recipes.

### 2.3 Evolving cooking notebook

The notebook records the user's actual cooking experience.

- One entry per recipe, rather than a separate permanent entry for every attempt.
- Each recipe entry contains the recipe, date, rating, free-form comments, changes made, and ingredient substitutions.
- The history of attempts is retained to track adjustments and how the recipe evolves.
- A recipe enters the notebook only after it has actually been cooked.

The notebook is not a library of every AI-generated suggestion: it represents recipes that have really been tried.

### 2.4 Personalization from experience

There is no long initial questionnaire about tastes, dietary restrictions, or habits.

The initial inventory already provides some clues about the user's cooking habits. Personalization should then emerge gradually from real feedback.

For the MVP, the logic should remain simple and explainable:

- Prefer recipes that have received good ratings.
- Reuse adjustments that the user has liked.
- Provide the AI with relevant successful recipes and their useful adjustments when generating new suggestions.

A more general preference summary can be considered later if early experiments show that it adds real value. No model training or opaque learning system is needed for the MVP.

### 2.5 Single-user scope

The MVP targets one user, with one inventory and one cooking notebook. Multi-user accounts and shared household inventories are out of scope for now.

## 3. Proposed interface

A hybrid web interface with three structured areas:

1. **Inventory** — view and edit ingredients and quantities.
2. **Suggestions** — view recipe suggestions, request recipes, and identify ingredients that should be used soon.
3. **Notebook** — revisit cooked recipes and their history.

A conversational input field allows the user to request recipes or update the inventory in natural language.

### Tools under consideration

- **Lovable** to generate the frontend, reusing the workflow explored in the Zoomcamp.
- A **coding agent** for the backend, integration, and required changes.
- The coding agent should explain its technical choices and avoid over-engineering.
- **Database choice remains open.** Starting with SQLite may speed up development, followed by a migration to PostgreSQL when appropriate, as in the Zoomcamp learning path. The data-access layer should be kept clean enough to make that transition manageable.

No final frontend/backend stack has been selected yet.

## 4. AI architecture and reliability

The selected approach is **Option B: use AI for recipe generation and natural-language interpretation, while conventional code manages the inventory and notebook**.

Principles:

- AI generates recipes and interprets natural-language instructions.
- Data operations are structured, validated, and applied by deterministic code.
- AI outputs are checked before being used.
- If an output is invalid, the application attempts a correction or retry, with no more than one retry.
- If the problem persists, the application explains what went wrong and reports the incident.

Monitoring should detect repeated errors and enable a controlled corrective action. A monitoring agent may act only within explicitly authorized limits. It must not arbitrarily alter inventory or other business data.

Incidents are:
- recorded in technical logs;
- shown in the application when user intervention is required.

External notifications, such as email, are out of scope for the MVP.

## 6. Scope and prioritization

The estimated time budget is approximately **20 hours**.

The agreed priority is **Option B: reduce some cooking features if needed to ensure all Zoomcamp technical requirements are met**.

The project should remain genuinely useful, but a small, reliable end-to-end workflow is preferable to a long list of unfinished features.

Proposed functional priorities:

1. A usable and reliable inventory.
2. Recipe generation adapted to the inventory, including quantities, servings, missing ingredients, and substitutions.
3. Saving a recipe that has actually been cooked, including its rating and adjustments.
4. Basic personalization based on successful recipes.
5. UI polish and secondary features, only if time allows.

Mandatory Zoomcamp engineering criteria should be built into the plan from the beginning, not left until the end.

## 7. Decisions made and open questions

### Decisions made

- Project name: **SavorLoop**.
- GitHub repository: https://github.com/YannPhamVan/SavorLoop
- Cooking assistant focused on inventory and an evolving cooking notebook.
- Two inventory categories: binary pantry staples and quantified rotating ingredients.
- Expiry dates are optional.
- Recipes are generated on demand; no pre-built recipe catalogue is needed.
- Prioritize urgent ingredients when relevant information is available.
- Recipes may require one or two missing ingredients.
- The notebook contains only recipes that have actually been cooked.
- One recipe entry with a history of attempts.
- No initial taste questionnaire.
- Simple personalization based on ratings and appreciated adjustments.
- Hybrid interface: structured pages plus conversational input.
- Inventory updates through both conventional controls and natural language.
- Single-user MVP.
- AI is used for suitable tasks; deterministic code handles business rules and data changes.
- Validate AI outputs, retry once, monitor failures, and display alerts.
- In-app alerts only; no email notifications.
- Lovable is planned for the frontend, with a coding agent for the backend and integration.
- Database choice remains open: SQLite initially, PostgreSQL later if appropriate.
- Estimated budget: approximately 20 hours.
- If trade-offs are required, Zoomcamp completion criteria take priority over secondary cooking features.

### Open questions

- Final frontend and backend stack.
- AI model/API and inference budget.
- Hosting and deployment platform.
- Whether and when to migrate from SQLite to PostgreSQL.
- Data schema and unit formats.
- Concrete validation rules for generated recipes and their consistency.
- Exact monitoring-agent responsibilities and permitted actions.
- Complete official grading criteria, to be checked against the Zoomcamp README.
- Detailed schedule for the approximately 20 hours and acceptance criteria for each stage.

## 8. Recommended next steps

1. Check the official Zoomcamp final-project README and turn every criterion into a verifiable checklist item.
2. Define the smallest viable MVP and its acceptance criteria.
3. Design the user journey and the screens to generate with Lovable.
4. Establish a minimal architecture for the frontend, backend, database, and AI calls.
5. Plan tests, observability, alerts, and agent response from the start.
6. Break the work into small tasks for the coding agent, with regular validation by the user.
7. Reserve time for fixes, deployment, and the required peer reviews.

## 9. Working principles for the rest of the project

- Work iteratively, addressing one important question or decision at a time.
- Avoid producing an exhaustive technical specification before verifying the official requirements.
- Ask the coding agent to propose and justify technical choices without allowing it to expand the scope unprompted.
- Validate features as they are implemented.
- Prefer a simple, testable, deployed solution over an ambitious but incomplete one.
- Emphasize user value and engineering quality in the README and demo.
